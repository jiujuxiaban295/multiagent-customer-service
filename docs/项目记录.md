### P1 多路召回去重失效 · 已解决（2026-10-04）

- **问题**：`MCPToolManager.search_with_rewrite` 把原问题和 3 个改写子查询的召回结果合并后，用整条结果的 md5 去重。但每条结果都带相似度分数，同一个片段被不同子查询召回时分数不同，所以去不了重。重排看到的是重复片段，最终返回的前 `top_k` 条里可能有重复，挤掉了其他有用片段。
- **解决方案**：`KnowledgeBase.search` 的返回结果加上 ChromaDB 的片段 `id`，`search_with_rewrite` 改为按 `id` 去重。没有 `id` 的结果（如知识库不可用时的降级结果）沿用原来的方式。`id` 放在结果字典的最后，避免挤占重排时每条结果 200 字的截断窗口。
- **为什么不按"标题 + 片段序号"去重**：片段 ID 是 `md5(标题_序号_内容前 50 字)`，标题和序号相同的片段可以同时存在多条，例如两篇同名文档（见 P2）。
- **验证**：
  - 新增 `tests/test_knowledge_base.py::test_search_returns_chunk_id`，以及 `tests/test_tool_manager.py` 中的 2 个测试。
  - 全部 16 个测试通过。
  - 把修复前的 `tool_manager.py` 换回去重跑，新测试失败（结果里出现重复的 `chunk-refund`），说明测试确实能发现这个问题。
- **相关文件**：`mcp/knowledge_base.py`、`mcp/tool_manager.py`、`tests/test_knowledge_base.py`、`tests/test_tool_manager.py`
- **备注**：Docker 里正在运行的服务还是旧代码，重建镜像后生效。

### P3 Docker 容器内访问不到宿主机上的本地模型 · 已解决（2026-10-04）

- **问题**：`.env` 里 `ANTHROPIC_BASE_URL=http://127.0.0.1:1234`（LM Studio）。在容器里，`127.0.0.1` 指向容器自己，所以运行中的服务实际连不上模型，所有模型调用都会失败、走兜底逻辑。最近一次 `/chat` 请求耗时 2.7 秒，且没有任何工具调用。
- **验证**：在 `echomind-app` 容器内访问 `127.0.0.1:1234` 失败；访问 `host.docker.internal:1234` 返回 200。
- **解决方案**：回答生成改用 DeepSeek（公网地址，不受影响）。之后用本地模型打分时，容器内的地址改用 `http://host.docker.internal:1234`。
- **状态**：`.env` 已切换为 DeepSeek（`https://api.deepseek.com/anthropic`，模型 `deepseek-v4-pro`），镜像重建后服务正常。晚上用本地模型打分时，容器内使用 `host.docker.internal:1234`。

### P4 LLM-as-Judge 打分全部失败 · 待排查

- **问题**：`data/eval/baseline.json`（2026-08-28）里 7 条对话评测都是 0.5 分，即打分失败时的默认值，`judge_failed` 均为 true，错误都是 `Expecting value: line 1 column 1 (char 0)`。整次评测的回复质量结果无效。
- **原因（已查明，见 P13）**：`LLMJudge.judge` 截取第一个 `{` 到最后一个 `}` 再解析 JSON。DeepSeek 默认开启推理，`max_tokens=256` 全部被推理内容占满，正文为空，找不到 `{`，于是报 `Expecting value`。
- **解决方案**：评测阶段改为按要点打分的新裁判，用本地模型打分，并记录每次打分的原始输出，便于排查。

### P8 知识库默认向量模型对中文效果一般 · 已解决（2026-10-04）

- **问题**：知识库使用 ChromaDB 默认的 all-MiniLM-L6-v2，基本只适合英文。知识库扩到 26 篇后问题暴露：评测集里有依据文档的 27 道题，纯向量召回只有 14 道能把正确文档排进前 5，发票、退款到账、重复扣款几题排在第 24–26 名（等于随机）。
- **诊断**：问题出在召回，不在重排——正确片段只要进了候选集，LLM 重排都能把它排进前 5。完整链路（改写 → 每个子查询召回 5 条 → 去重 → 重排）只有 19/27；每个子查询召回 10 条是 23/27。LM Studio 现成的 nomic-embed-text-v1.5 也只有 14/27。
- **解决方案**：知识库改用 bge-m3（LM Studio 加载 `gpustack/bge-m3-GGUF` 的 Q8_0，635 MB，通过 OpenAI 兼容的 `/v1/embeddings` 调用）。
  - `KnowledgeBase` 新增可选的向量模型配置（`ECHOMIND_EMBEDDING_MODEL`、`ECHOMIND_EMBEDDING_BASE_URL`，已写入 `.env`）；配置后用单独的集合 `knowledge_base__text_embedding_bge_m3`，按余弦距离建索引；不配置时行为不变。
  - 效果：纯向量召回前 5 命中 27/27，完整链路 27/27。召回条数改成可配置（`ECHOMIND_RAG_RECALL_K`），默认仍为 5。
- **代价**：线上服务的检索依赖本机 LM Studio，LM Studio 没开时知识库走降级结果。记忆模块（情景记忆、用户画像）仍用默认向量模型，没有改。
- **备注**：运行中的 `echomind-app` 还是旧镜像，重建镜像后才会用 bge-m3；评测脚本挂载当前代码，已经在用。

### P12 检索相似度分数口径错误 · 未处理

- **问题**：知识库集合创建时没有指定距离类型，ChromaDB 默认用 L2 距离；但 `KnowledgeBase.search` 按余弦距离把分数换算成 `1 - 距离`，L2 距离大于 1 时分数为负。冒烟测试里 5 个片段的分数在 -0.17 到 0 之间，没有参考意义。
- **影响**：同一次查询内的排序不受影响（距离越小越靠前）；但分数不能当相关度用，也不能跨查询比较。
- **当前处理**：V1 提示词里不展示分数，资料按检索（重排）后的顺序编号；返回结果里的 `retrieved` 仍保留原始分数供分析。
- **解决方案（之后）**：创建集合时指定 `metadata={"hnsw:space": "cosine"}`（需要重建集合），或按 L2 距离换算分数。
- **进展**：bge-m3 的新集合已按余弦距离建索引，分数就是余弦相似度；默认集合（不配置向量模型时使用）没有改。

### P13 DeepSeek 默认开启推理导致多个模块静默降级 · 已解决（2026-10-04）

- **问题**：`deepseek-v4-pro`、`deepseek-flash` 通过 Anthropic 兼容接口调用时默认开启推理，推理内容计入 `max_tokens`。项目里意图识别、查询改写、重排、记忆摘要、打分这些调用都只给 256 token，推理内容会把额度用完，正文为空，代码解析失败后走兜底：
  - 意图识别的 LLM 一路失败，只剩字符向量和关键词两路（旧评测基线里的 "LLM 失败" 即此原因）；
  - 查询改写失败，只用原问题检索；
  - 重排失败，按原召回顺序截取；
  - 记忆摘要失败，写入"摘要生成失败"；
  - 打分失败，全部 0.5（P4）。
- **验证**：用意图识别同款提示词、`max_tokens=256` 实测，两个模型各调用 2 次，默认情况下 4 次都是 `stop_reason=max_tokens`、只有推理块、正文为空；加上 `thinking: {"type": "disabled"}` 后，约 3 秒返回正确的 JSON。
- **解决方案**：`core/llm_utils.make_client` 默认给每次调用加上 `thinking: disabled`。项目使用的 anthropic SDK 0.40 没有 `thinking` 参数，通过 `extra_body` 传。环境变量 `LLM_THINKING=enabled` 可恢复服务端默认行为。三个版本使用同样设置，对比公平。本地 LM Studio 也接受该参数。
- **效果**：镜像重建后用 DeepSeek 冒烟测试，日志中不再出现改写、重排、意图识别失败的警告；V1 的查询改写正常产出 3 个子查询。
- **测试**：新增 `test_disable_thinking_adds_extra_body_without_dropping_caller_options`。

### P14 跨会话记忆检索每次都失败 · 未解决

- **问题**：`MemoryManager._search_episodic` 的第一次查询用 `where={"user_id": ..., "conv_id": ...}`。ChromaDB 要求多个条件用 `$and` 组合，所以每次都抛 `Expected where to have exactly one operator`。异常被捕获后直接返回空列表，后面"只按用户过滤"的兜底查询也执行不到。结果是跨会话检索从未生效，只有 Redis 里当前会话的记忆在起作用。
- **影响**：今晚的多轮评测（最多 3 轮）使用当前会话的 Redis 记忆，不受影响。简历中"旧对话写入 ChromaDB 供跨会话检索"的说法，在修复前不成立。
- **解决方案**：改为 `where={"$and": [{"user_id": ...}, {"conv_id": ...}]}`，并补测试。

### P15 监控误降权可能触发路由回退 · 未解决（评测时绕开）

- **问题**：
  1. `AgentStats.total` 在请求开始时加 1，`success` 在请求结束时才加 1。监控每 10 秒采样一次，如果采样时请求还在执行，就会被算成失败。冒烟测试中监控报了"技术 Agent 成功率 0"，实际那次调用是成功的。
  2. 降权公式中，平均耗时超过 3 秒就开始罚分，最多罚 0.4；带工具调用的 LLM Agent 一次本来就要 5–15 秒，光延迟一项就接近上限。
  3. 罚分达到 0.5 时，技术或账单 Agent 会被移出路由、回退到通用 Agent。样本少时，第 1 点可能单独触发回退；样本多时，第 1、2 点叠加也会触发。
- **影响**：线上会出现误报和误回退。评测时如果开着监控，V3 的路由会随监控状态变化，结果不可复现。
- **当前处理**：评测脚本自己组装三个版本，不启动监控。
- **解决方案（之后）**：`total` 改为在请求结束时计数（或单独统计执行中的请求）；延迟阈值改成可配置，并按 LLM Agent 的实际耗时设定。

### P16 Agent 调用工具那一轮的文字被丢掉 · 已解决（2026-10-04）

- **问题**：`BaseAgent._call_llm` 的工具调用循环只返回最后一轮回复的文字。模型在调用工具的那一轮先写给用户的内容（例如先列出"需要提供的 5 项信息"，再调用转人工工具）被丢掉，用户看到的回复里写着"把上面 5 项信息补充给我"，上面却什么都没有。V2、V3 都受影响，V1 不调用工具，不受影响。
- **发现**：评测冒烟测试 D02（账号被盗）V2 的回答。
- **解决方案**：循环里按顺序收集每一轮的文字，最后用空行拼接返回。新增测试 `test_agent_keeps_text_written_alongside_tool_calls`。
- **影响**：运行中的服务要重建镜像才生效；评测使用修复后的代码。

### P17 转人工标记靠关键词匹配，误报多 · 未解决

- **问题**：`detect_handoff` 只要回复里出现"转人工""人工客服"等词就记为转人工。"如果超过 7 个工作日仍未到账，可以联系人工客服核实"这种条件性的后续建议，也会被记成转人工。冒烟测试里 V3 回答积分计算题也被记成了转人工（日志里的"触发升级"）。
- **当前处理**：评测里是否转人工由裁判按语义判断，系统的 `escalated` 字段只作参考，报告里两者分开统计。
- **解决方案（之后）**：转人工以调用 `create_handoff_summary` 工具或路由到升级节点为准，不再用关键词。

## 四、V1 实现计划：单轮 RAG（已实现，2026-10-04）

> 完整设计（含 V2、统一接口、接口改动）见 [docs/架构演进实现计划.md](docs/架构演进实现计划.md)，两份文档保持一致。

### 4.1 定位

三个版本中最简单的基线：检索一次，生成一次。没有工具、Skills、记忆，也没有意图识别和路由。用来和 V2（单 Agent）、V3（多 Agent）对比，说明后续架构各自带来的收益和代价。

### 4.2 流程

```text
用户消息 → RAG hook（复用现有 RAG 工具）→ 拼提示词 → 一次回答生成 → 返回
```

### 4.3 RAG hook：复用现有工具，不重写检索逻辑

- 取 `build_shared_rag_tools(tool_manager)["search_knowledge_base"]`，在生成前直接调用它的 handler：`await spec.handler(req, {"query": message, "top_k": 5})`。这和 V2、V3 的 Agent 调用的是同一段代码。
- 工具内部走现有的 `search_with_rewrite`：LLM 把问题改写成 3 个子查询（连同原问题共 4 条）→ 并行向量召回（每条取前 5）→ 按片段 ID 去重（P1 修复后）→ 召回结果多于 `top_k` 时用 LLM 重排 → 取前 `top_k` 条。
- `top_k` 默认 5，与 Agent 调用这个工具时的默认值一致，可配置。
- 记一条与 Agent 工具调用格式相同的轨迹（`tool_name`、`input`、`success`、`latency_ms`、`reranked`），另加 `"source": "hook"`。
- 降级：工具返回 `success: false`，或结果带 `fallback` 标记时，按"没有检索到资料"处理。

### 4.4 提示词（草稿）

system：

```text
你是电商平台的智能客服。请根据【参考资料】回答用户的问题：
1. 资料里有的信息要准确引用，不要改动数字和条件；
2. 资料里没有的信息，尤其是用户本人的订单、物流、支付、退款状态，不要编造，直接说明无法确认，并建议用户提供订单号或联系人工客服；
3. 先回应用户的核心问题，语言简洁。
```

user：

```text
[参考资料]
1. 《退款政策》
……片段内容……
2. ……

[用户问题]
……
```

- 资料按检索（重排）后的顺序编号，不展示相似度分数：分数口径有误，会出现负值（见 P12）。
- 没有检索到资料时，`[参考资料]` 下写"（未检索到相关资料）"。

### 4.5 不做的事

不读写记忆，不做意图识别，不注入 Skills，生成调用不传 `tools` 参数，没有澄清和降级 Agent。

### 4.6 模型调用次数

改写 1 次 + 重排 0–1 次 + 生成 1 次，共 2–3 次。"单轮"指一次检索加一次生成，不是只调用一次模型，用量统计里会如实体现。

### 4.7 统一接口与输出

新文件 `agents/pipelines.py` 中的 `RagBaselinePipeline`，实现 `async run(inp: PipelineInput) -> PipelineResult`：

- `response`：回答文本。
- `tools_used = ["search_knowledge_base"]`，`tool_traces` 为 hook 的那一条。
- `retrieved`：检索到的片段（标题、分数、片段序号、ID）。
- `escalated`：与 `BaseAgent` 相同的关键词判断（回复里出现"转人工""人工客服"等）。
- `llm_calls`、`input_tokens`、`output_tokens`：本次请求的模型用量。

### 5.5 设计决策（2026-10-04）

- **Skills**：保持原项目的机制。按关键词匹配，命中的 Skill 全文注入系统提示词，不做 skill lookup 工具，也不做渐进式披露（按需加载）。V2 合并所有命中的 Skill（总长度受 5000 字上限约束），V3 每个垂类 Agent 只注入适用于自己的 Skill（现状不变）。

## 六、架构对比评测（2026-10-04 晚）

### 6.1 评测脚本

`evaluation/arch_eval.py`，在应用镜像的临时容器里运行，和线上服务连同一个 Redis、ChromaDB：

```bash
docker run --rm --network echomind_echomind-network --env-file .env -v "$PWD":/app echomind-echomind python -m evaluation.arch_eval --out data/eval/runs/<名称>
```

- **生成**：按 `api/main.py` 的方式自己组装三个版本；不启动监控（P15）；检索不缓存（P9）；多轮题按顺序发送，前几轮的回复由被测版本实时生成；V2/V3 每轮前读记忆、回答后写回，与 `/chat` 一致，V1 不读写记忆；回答后的用户画像更新不做。每题每个版本用独立的用户和会话。同一题的三个版本相邻排队，并发 3。

- **报告**：`report.md`（总体、分类别、V3 意图识别、逐题结果、未通过明细）、`answers.md`（逐题对照三个版本的回答，供人工抽查裁判）、`summary.json`。
- **检索统计**：V2/V3 的工具轨迹里没有检索结果，评测时给检索工具包了一层记录，三个版本统一统计"最后一轮是否检索、是否命中依据文档"。

### 6.2 冒烟测试（3 题 × 3 版本）
