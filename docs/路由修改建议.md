# 路由修改建议与实施记录

> 日期：2026-10-04（Asia/Hong_Kong）
> 状态：**已实施**
> 代码：`app/routing.py`、`app/runtime.py::_handoff`、`app/retrieval.py::section`、`app/main.py`
> 数据：`docs/jev-routing-calibration.json`（78 条样例的真实 Jev 回答，其中 16 条多轮样例的上下文来自真实 `/chat` 对话）、`docs/routing-verification.json`（最终代码复测）
> 脚本：`.venv/bin/python -m scripts.calibrate_routing`、`.venv/bin/python -m scripts.verify_routing`（都会调用真实 Jev）

## 1. 结论

- **Jev 有效时只按 Jev 路由，Jev 不可用时才用关键词兜底**，两种模式不混合打分。原先"0.7 × Jev 相关概率 + 0.3 × 关键词分"的融合规则，以及"关键词信号在 Jev 模式下强制升级"的做法都已取消。
- Jev 一次请求回答三类问题：五选一主意图、四个领域各自独立的相关概率、用户是否明确表示紧急。主角色用五选一的结果，辅助角色看领域相关概率；选 escalation，或明确紧急，就交给人工。
- 升级节点仍不调用生成模型（和原项目一致），但会按升级原因附上知识库里对应章节的止损说明，也不再向用户展示内部字段。
- 门槛按真实 Jev 样例设定。最终代码在 78 条样例上的结果：Jev 模式 75/78，14 条应升级的全部升级，误升级 0；关键词兜底 73/78，误升级 0。门槛和复测用的是同一批样例，所以这是一致性检查，不是留出集上的准确率。
- 16 条多轮样例使用真实对话上下文（前几轮跑真实 `/chat`，包括 DeepSeek 生成的客服回复），Jev 模式和兜底模式都是 16/16。

## 2. 修改前的问题

| 问题 | 证据 |
|---|---|
| 判定不单调 | 消息不含关键词，Jev 选通用。技术相关概率为 0.85 时被要求澄清，0.70 时技术和通用并行，0.60 时只用通用 |
| Jev 五选一没被用来选主角色 | Jev 以 0.8 的概率选技术，但技术相关概率 0.7，融合后 0.49 < 0.5，结果是澄清 |
| 升级只覆盖"要人工"和"账号被盗" | 知识库「人工客服与投诉」列出的商品安全、被骗转账、投诉升级都会进澄清 |
| 升级回复展示内部字段、没有止损 | 回复里出现 `explicit_human_request`、`UNKNOWN`、重复的实体键名；账号被盗时没有"重置密码、冻结账户"之类的建议 |
| 关键词兜底覆盖差 | 原项目 30 题只走关键词：对 20、澄清 8、判错 2；"你好，我想退款"因为问候语和"退款"打平而澄清 |
| 续接借分 | "怎么办"会让新问题套用上一轮的领域；只看上一条用户消息，借不到更早的上下文 |
| 正则把"能不能"当否定 | "能不能帮我转人工""能不能找你们经理"不升级（原有 bug，本次修复） |

## 3. 最终规则

### 3.1 Jev 模式

| 顺序 | 条件 | 结果 | 常量 |
|---|---|---|---|
| 1 | 紧急概率 ≥ 0.8 | 人工升级，原因 `jev_urgent` | `JEV_URGENT_THRESHOLD` |
| 1 | 选 escalation，且选项概率 ≥ 0.6、升级相关概率 ≥ 0.6 | 人工升级，原因 `jev_escalation` | `JEV_ESCALATION_CHOICE` / `JEV_ESCALATION_RELEVANCE` |
| 2 | 选 unknown，概率 ≥ 0.5 | 通用角色澄清 | `CHOICE_PRIMARY_THRESHOLD` |
| 3 | 选通用、技术或账单，概率 ≥ 0.5 | 该角色为主角色，`primary_source=jev_choice` | `CHOICE_PRIMARY_THRESHOLD` |
| 4 | 五选一不够确定 | 取相关概率最高的领域（平局时技术 → 账单 → 通用），低于 0.5 则澄清，`primary_source=jev_relevance` | `PRIMARY_THRESHOLD` |
| 5 | 技术、账单中非主角色的一方，相关概率 ≥ 0.85 | 作为辅助角色并行 | `JEV_SUPPORT_THRESHOLD` |

Jev 模式下，关键词分和升级正则**不改变路由**。正则命中的信号只记录在 `signals` 里，用于给升级回复选择对应的知识库章节。

### 3.2 关键词兜底模式

在 Jev 超时、网络或 HTTP 错误、返回不合法、未配置凭证时使用：

1. **升级信号**，按以下优先级：明确要人工 → 账号或资金安全 → 诈骗 → 商品安全 → 投诉或法律纠纷 → 紧急（`紧急|urgent|emergency|asap`）。识别时：
   - 排除否定、引用、预防性和已解决的表述；
   - "能不能 / 可不可以 / 要不要"按疑问句处理，不当作否定；
   - 投诉前面出现"怎么 / 如何 / 在哪 / 哪里"时，按流程咨询处理，不升级。
2. **领域打分**：词表以知识库章节为来源，每个正则组只计一次权重，除以 3 并封顶为 1。问候语不计分；有意不收单独的"登录""退"字和"更新"。
3. **续接**："还是不行 / 仍然不行 / 还是一样"等，且本句关键词分低于 0.5 时，向前最多看 3 条用户消息借分（乘以 0.8），都没有就看会话摘要。"怎么办""继续"不再算续接。
4. **主角色**：关键词分最高者，平局时技术 → 账单 → 通用；低于 0.5 则澄清。
5. **辅助角色**沿用原项目规则：先看技术、账单协作关键词；没有命中时，再看分数 ≥ 0.45 且不低于主角色的 55%。

### 3.3 Jev 题面

- **escalation**：需要人工处理的情况，包括主动要求人工或经理；账号被盗、诈骗或已发生资金损失；正在发生或已发生的商品安全事件；正式投诉或法律纠纷。描述里明确说明：询问如何预防、如何投诉、人工服务时间，都不算升级。
- **general**：补充账户设置（换绑手机、注销）、会员与积分。
- **urgent**（新增的独立问题）：用户是否明确表示当前问题紧急。描述里明确说明"立刻 / 马上"只用于描述普通诉求（如尽快发货、取消订单）时不算紧急。

### 3.4 升级出口（`app/runtime.py::_handoff`）

- **原因代码**：有正则信号时用信号名，没有时用路由原因。按下表对应到中文原因和知识库章节，章节按标题精确读取，不走向量检索：

  | 原因代码 | 中文原因 | 知识库章节 |
  |---|---|---|
  | `explicit_human_request` | 您要求人工客服处理 | 人工客服与投诉 |
  | `complaint` | 投诉或纠纷需要人工客服跟进 | 人工客服与投诉 |
  | `security_risk` | 账号或资金存在安全风险 | 账号被盗与异常登录 |
  | `fraud` | 疑似诈骗或已发生资金损失 | 防诈骗提醒 |
  | `product_safety` | 商品存在安全隐患 | 商品安全问题 |
  | `urgent` / `jev_urgent` | 您说明情况紧急 | 人工客服与投诉 |
  | `jev_escalation` 及其他 | 需要人工客服进一步核验 | 人工客服与投诉 |

- **回复内容**：只展示中文原因、有值的订单号 / 金额 / 日期 / 错误码，紧急时加上"优先级：紧急"。知识库读取失败时省略止损段落，其余照常返回。
- **交接摘要**：紧急时 `urgency=CRITICAL`，否则 `UNKNOWN`。

### 3.5 `RouteDecision` 新增字段

| 字段 | 取值 |
|---|---|
| `primary_source` | `jev_choice` / `jev_relevance` / `keyword` / `jev`（升级）/ `clarify` |
| `signals` | 命中的升级正则及原文片段（Jev 模式下仅作诊断） |
| `urgent` | Jev 模式下取紧急概率 ≥ 0.8；兜底模式下取正则 |
| `inherited_from` | 续接借分的来源，如 `user_message:-2` 或 `summary` |

`routing_reason` 在 Jev 模式下由 `jev_keyword_fusion` 改为 `jev`，其余取值不变。`extra.routing_scores` 在 Jev 模式下是 Jev 的领域相关概率，在兜底模式下是关键词分。

## 4. 决定记录

| 事项 | 决定 | 说明 |
|---|---|---|
| 路由依据 | Jev 优先，关键词只作兜底 | 用户决定。真实数据表明，否定和引用类句子 Jev 自己就能判对，不需要正则来否决 |
| 紧急 | 直接升级 | 用户决定，与原项目一致。Jev 模式由独立的紧急问题判断；兜底模式不收"立刻"，因为实测"能立刻发货吗""我想立刻取消订单"会被误升级 |
| 账户管理（换绑、注销） | 归通用 | 用户决定。知识库把它们放在「更换绑定手机号」「隐私保护与身份核验」 |
| 并行 | 兜底模式沿用原项目规则 | 用户决定。Jev 模式按"Jev 优先"的决定改用 Jev 相关概率，原项目的关键词并行规则只在兜底时生效 |
| 关键词平局 | 专业角色优先 | 用户决定 |
| 选中领域的相关概率下限 | 不设 | 实测唯一受影响的是 X35"人工客服几点上班"：Jev 以 0.68 选通用，但通用相关概率只有 0.32，加下限反而判错 |
| 多轮校准 | 用真实对话上下文 | 用户决定。前几轮跑真实 `/chat`，最后一轮用会话存储的快照路由，与线上发给 Jev 的内容一致 |
| 发给 Jev 的用户原话 | 原样发送，不脱敏 | 用户决定。用户在消息里写的订单号、手机号等会出现在发给 Typesafe.ai 的请求中 |

## 5. 校准过程与实测

### 5.1 样例

共 78 条，每条在最后一轮调用一次真实 Jev（`jev-1.13.0`）：

- 原项目 30 题：取末轮消息；
- 40 条自拟（X01–X40）：升级正例，否定、引用、预防类反例，问候，账户管理，复合问题，续接，"立刻"类普通诉求；
- 8 条自拟多轮对话（M01–M08）：专门检验"客服回复里提到人工"、"上一轮转人工或紧急"、"问题已解决后换话题"是否会把下一轮带偏。

上下文的构造方式：

- **单轮样例**（62 条）：历史和摘要都为空，与线上第一轮相同。
- **多轮样例**（16 条：F01–F06、X29、X30、M01–M08）：前几轮通过真实 `/chat` 运行，包括 Jev 路由、DeepSeek 生成回复、真实知识库，会话存储为隔离的临时 SQLite；最后一轮用存储里的快照调用路由，Jev 收到的最近消息包含客服回复，和线上一致。这些对话最多 3 轮，没有触发会话摘要压缩，所以摘要为空。

标签是对路由结果的预期，不是回答质量。前两轮校准（5.2、5.3）时，多轮样例的历史里只放了用户消息；第三轮（5.4）改为真实对话上下文。

### 5.2 第一轮（原题面）

- 主角色：30 题中 29 题由五选一选对。
- 升级：10 个升级正例，Jev 都选了 escalation；否定类反例都没有误判。
- 3 个问题：
  - "紧急！支付失败了"被选为账单，没有升级；
  - "怎么防止充电宝起火"被选为 escalation；
  - "找你们经理"的升级相关概率只有 0.82。
- 领域相关概率普遍偏高：A03"加急配送多少钱"的账单相关 0.83，X20"换绑手机号"的技术相关 0.82，所以 0.45 不能用作 Jev 模式的辅助门槛。

### 5.3 第二轮（改题面并加入紧急问题），据此确定门槛

| 门槛 | 依据 |
|---|---|
| 紧急 0.8 | 3 个明确紧急的样例为 0.98–0.99，其余 67 条 ≤ 0.28 |
| 升级 0.6 / 0.6 | 13 个升级样例中，选 escalation 的概率都 ≥ 0.95，相关概率最低 0.83（X01）；没有反例被选为 escalation |
| 主角色 0.5 | 正确选择中概率最低的是 0.56；低于 0.5 的只有 X10、X26、X39，改为按相关概率判断 |
| 辅助 0.85 | 需要并行的样例，次要领域相关概率最低 0.86（C02、X27）；不该并行的最高 0.84（A03）。**余量很小** |

### 5.4 第三轮：多轮样例改用真实对话上下文

门槛不变。16 条多轮样例的前面一共 24 轮，全部由真实 `/chat` 生成回复：20 轮是 DeepSeek 写的回答，4 轮是升级节点的回复。其中 18 轮提到了"人工"，正好可以检验"客服回复提到人工，会不会把下一轮带成升级"。结果：

- **客服回复提到人工后，没有误升级**：
  - F02、M01 的升级相关概率是 0.31–0.32，五选一都是账单，概率 1.0；
  - 其余没有要求人工的多轮样例，升级相关概率都 ≤ 0.09。
- **转人工和紧急都不会延续到下一轮**：
  - M02：上一轮转人工，这一轮"算了不用人工了，我自己查下退款进度"，判为账单；
  - M05：上一轮"紧急！支付失败了"，这一轮"现在支付成功了，发票怎么开"，紧急概率 0.07，判为账单；
  - M03："还是不行，给我转人工"，升级。
- **问题已解决后换话题**：M07 判为通用。上一轮是 401 的问题时，问"尺码不对"（X29）判为通用，说"还是不行"（X30）判为技术。
- **两可的情况**：M04 上一轮账号被盗，这一轮问被盗刷的钱怎么退。Jev 以 0.51 选账单，升级相关概率 0.96，路由到账单。标签允许账单或升级。0.51 紧贴 0.5 门槛，这类样例需要更多数据。
- 前一次运行时，执行环境里的 `ANTHROPIC_BASE_URL` 盖过了 `.env`，生成调用失败，得到的数据已作废并重跑，见第 7 节。

|---|---|---|---|---|---|
| Jev | 75/78 | 14/14 | 0 | 4 | 0 |
| 关键词兜底 | 73/78 | 14/14 | 0 | 9 | — |

多轮样例：两种模式都是 16/16。

- **Jev 模式未对上的 3 条**：
  - C02：主角色给了通用，账单作为辅助仍会处理；
  - X10"怎么防止充电宝起火"：给了技术，没有升级；
  - X39"怎么防止被骗"：进了澄清。
- **兜底模式未对上的 5 条**：都是"怎么投诉商家""怎么防止…""人工客服几点上班"这类没有关键词的问法，结果是澄清，最终仍由通用角色接待。

- **升级出口实测**：用真实 Jev 和真实知识库测了三句话，"紧急！支付失败了""充电宝冒烟""冒充客服转账"分别附上了「人工客服与投诉」「商品安全问题」「防诈骗提醒」，选对了章节。

## 6. 测试

自动测试共 84 项，全部通过：

- **改写**：旧测试里假设"Jev 模式下关键词也参与"的部分（融合、正则覆盖升级、关键词并行），改为分别测"兜底模式的关键词行为"和"Jev 模式只按 Jev"。
- **新增**：
  - Jev 门槛：主角色、升级、紧急、辅助 0.85；
  - 判定单调性：相关概率越高越不会进入澄清；
  - 五选一不确定时按相关概率判断；
  - 兜底模式：问候语、知识库词表、升级信号及其反例、"能不能"疑问句、续接回看；
  - 升级出口：附止损章节、不展示内部字段、知识库读取失败时的降级。

## 7. 遗留问题与后续

1. **留出集**：门槛在同一批 78 条上设定并复测。建议另写 50 条以上不由现有样例改写的消息，用 `scripts.calibrate_routing --eval` 跑一遍后再确认门槛。
2. **辅助门槛余量小**：0.84 和 0.86 只差 0.02。Jev 版本或题面变化后，要先重跑校准脚本。
3. **预防类问题**：Jev 模式下"怎么防止…"类问题有时被给到技术，或进入澄清，不会升级，影响较小。
4. **Jev 依赖**：题面任何改动都会改变输出分布，修改后必须重新校准；`jev-1.13.0` 保持固定版本。
5. **环境变量优先于 `.env`**：`Settings.from_env()` 的 `load_dotenv()` 不覆盖已有的环境变量。如果进程环境里已有 `ANTHROPIC_BASE_URL`（例如在 Claude Code 中执行），DeepSeek 密钥会被发到 Anthropic，所有生成调用都返回 401。在这类环境里运行脚本要用 `env -u ANTHROPIC_BASE_URL`；是否改为让 `.env` 优先，或者改用项目专用的变量名，待决定。
6. **会话摘要未覆盖**：多轮样例最多 3 轮，没有触发摘要压缩，Jev 收到的 `session_summary` 都是空的。长对话中摘要对路由的影响还没有验证，需要补充 8 轮以上的样例。
7. **不在本次范围**：P16（工具调用轮的文字拼接）、`app/tools.py::request()` 的旧意图桥接，见此前的对齐检查结论。
