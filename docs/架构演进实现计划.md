# 架构演进实现计划：V1 单轮 RAG / V2 单 Agent

> 状态：V1、V2、统一接口和 `/chat` 切换已实现（2026-10-04），实现结果见 [项目记录.md](../项目记录.md) 第五节；第 9 节业务查询工具已取消（2026-10-04 决定）
> 评测：评测集、打分和对比实验见 [项目记录.md](../项目记录.md) 第六节，脚本为 `evaluation/arch_eval.py`；知识库改用 bge-m3（项目记录 P8）
> 范围：V1、V2 的实现，三个版本的统一接口，`/chat` 按版本切换，按请求统计模型用量
> 不在范围内：评测集、打分和对比实验（实现完成后另定）

## 1. 目标

在现有的多 Agent 系统（下称 V3）之外，补齐两个更简单的版本。三个版本实现同一个接口，之后在同一套评测集上对比回答质量、成本和延迟，用数据说明每一步架构演进的收益和代价。

## 2. 三个版本

| 版本 | 流程 | RAG | 工具 | Skills | 记忆 | 意图识别 / 路由 |
|---|---|---|---|---|---|---|
| V1 单轮 RAG | 固定流程：检索 hook → 一次回答生成 | 有，生成前固定执行 | ✗ | ✗ | ✗ | ✗ |
| V2 单 Agent | 一个 Agent 的工具调用循环 | 作为工具，由 Agent 决定是否调用 | ✓ 全部合并 | ✓ 命中的全部合并 | ✓ | ✗ |
| V3 多 Agent（现有） | 意图识别 → 路由 → 主辅 Agent 并行 → 汇总 | 作为工具 | ✓ 按领域分配 | ✓ 按领域分配 | ✓ | ✓ |

控制变量：三个版本使用同一个模型、同一个知识库、同一条 RAG 检索链路（查询改写 → 并行召回 → 去重 → 重排）、同一套工具实现。

- **V1 → V2**：检索从"每次固定执行"变成"Agent 自己决定"，同时加入工具、Skills、记忆和工具调用循环。这一步的提升是这几项的合力，不拆分各自的贡献。
- **V2 → V3**：只差意图识别、路由和多 Agent 并行协作。

## 3. 统一接口

新文件 `agents/pipelines.py`。三个版本都实现：

```python
async def run(self, inp: PipelineInput) -> PipelineResult
```

```python
@dataclass
class PipelineInput:
    message: str
    user_id: str
    conv_id: str
    context: str = ""                                    # 记忆上下文文本，V1 忽略
    history: Optional[List[Dict[str, str]]] = None       # 最近对话，V1 忽略

@dataclass
class PipelineResult:
    mode: str                     # "v1" / "v2" / "v3"
    request_id: str
    response: str
    success: bool
    escalated: bool
    tools_used: List[str]
    tool_traces: List[Dict[str, Any]]
    latency_ms: float
    llm_calls: int                # 本次请求实际发起的模型调用次数
    input_tokens: int
    output_tokens: int
    retrieved: List[Dict[str, Any]]   # V1：检索 hook 返回的片段（标题、分数、片段序号）
    extra: Dict[str, Any]             # V3：intent、routing_reason、primary_agent 等
```

| 类 | 版本 |
|---|---|
| `RagBaselinePipeline` | V1 |
| `SingleAgentPipeline`（内部使用 `SingleAgent`） | V2 |
| `MultiAgentPipeline`（包装现有 `AgentOrchestrator`） | V3 |

## 4. V1：单轮 RAG

### 4.1 流程

```text
用户消息 → RAG hook（复用现有 RAG 工具）→ 拼提示词 → 一次回答生成 → 返回
```

### 4.2 RAG hook：直接复用现有工具，不重写检索逻辑

- 取 `build_shared_rag_tools(tool_manager)["search_knowledge_base"]`，在生成前直接调用它的 handler：`await spec.handler(req, {"query": message, "top_k": 5})`。这和 V2、V3 的 Agent 调用的是同一段代码。
- 工具内部走现有的 `MCPToolManager.search_with_rewrite`：LLM 把问题改写成 3 个子查询（连同原问题共 4 条）→ 并行向量召回（每条取前 5）→ 合并去重 → 召回结果多于 `top_k` 时用 LLM 重排 → 取前 `top_k` 条。
- `top_k` 默认 5，与 Agent 调用这个工具时的默认值一致，可配置。
- 记一条与 Agent 工具调用格式相同的轨迹（`tool_name`、`input`、`success`、`latency_ms`、`reranked`），另加 `"source": "hook"`，方便和 V2、V3 的工具轨迹放在一起比较。
- 降级处理：工具返回 `success: false`，或结果带 `fallback` 标记（知识库不可用时的降级结果），都按"没有检索到资料"处理。

### 4.3 提示词（草稿）

system：

```text
你是电商平台的智能客服。请根据【参考资料】回答用户的问题：
1. 资料里有的信息要准确引用，不要改动数字和条件；
2. 资料里没有的信息，尤其是用户本人的订单、物流、支付、退款状态，不要编造，直接说明无法确认，并建议用户提供订单号或联系人工客服；
3. 先回应用户的核心问题，语言简洁。
```

user：

```text
[参考资料]
1. 《退款政策》
……片段内容……
2. ……

[用户问题]
……
```

资料按检索（重排）后的顺序编号，不展示相似度分数（分数口径有误，会出现负值，见项目记录 P12）。没有检索到资料时，`[参考资料]` 下写"（未检索到相关资料）"。

### 4.4 V1 不做的事

不读写记忆，不做意图识别，不注入 Skills，生成调用不传 `tools` 参数，没有澄清和降级 Agent。

### 4.5 模型调用次数

改写 1 次 + 重排 0–1 次 + 生成 1 次，共 2–3 次。"单轮"指一次检索加一次生成，不是只调用一次模型，这一点会体现在用量统计里。

### 4.6 输出

- `tools_used = ["search_knowledge_base"]`，`tool_traces` 为 hook 那一条。
- `retrieved` 记录检索到的片段。
- `escalated` 用与 `BaseAgent` 相同的关键词判断（回复里出现"转人工""人工客服"等）。

## 5. V2：单 Agent（无路由）

### 5.1 流程

```text
记忆上下文（接口层读取）→ 正则抽取实体 → SingleAgent 工具调用循环（最多 5 轮）→ 返回
```

### 5.2 SingleAgent（继承 `BaseAgent`）

直接复用 `BaseAgent` 的工具调用循环，包括工具白名单、JSON Schema 参数校验和调用轨迹。

- 新增 `AgentType.SINGLE = "single"`。
- `max_tool_rounds = 5`。V3 的各个 Agent 保持 3 轮。单 Agent 要一个人干两三个垂类 Agent 的活，轮数不够会导致复合问题直接失败。
- 温度 0.2，取 V3 各垂类 Agent（通用 0.3、技术 0.1、账单 0.0）的中间值；`max_tokens = 1200`。

角色契约（`AgentProfile`）：

| 字段 | 内容 |
|---|---|
| role | 全能客服（单 Agent，无路由） |
| mission | 由一个 Agent 完成理解诉求、查询事实、按业务规则回答和转人工判断，不区分领域 |
| workflow | 理解诉求并拆分问题 → 判断是否需要调用工具 → 调用工具获取事实 → 按业务规则逐项回答 → 判断是否需要转人工 |
| input_contract | 对话历史与用户画像；结构化实体；工具返回结果 |
| output_contract | 先回应核心问题；多个问题逐项回应；信息不足时只询问必要字段；明确下一步和边界 |
| handoff_conditions | 用户明确要求人工；账号安全或资金损失等高风险情况；投诉升级或涉及法律/监管表述；需要后台操作或人工审核 |
| tool_scope | 见 5.3 |

system_prompt（草稿）：

```text
你是电商平台的智能客服，需要独自处理咨询、订单物流、技术故障、账单退款和投诉转人工等所有问题。
需要事实依据时先调用工具查询，不要凭空编造订单、支付、退款等系统信息；
用户的问题包含多个方面时，逐项回应；
遇到需要人工处理的情况，调用转人工摘要工具，并明确告知用户。
```

`BaseAgent` 会在后面自动拼上角色契约和动态 Skills。

### 5.3 工具

- **包含**：`search_knowledge_base`（共享 RAG 工具）、`lookup_error_code`、`build_diagnostic_plan`、`check_billing_fields`、`compare_amounts`、`create_handoff_summary`。不新增业务查询工具（见第 9 节）。
- **不包含**：`inspect_request_context`、`suggest_required_fields`。这两个工具读的是意图识别的结果，V2 没有路由，它们拿不到数据。

### 5.4 Skills

- 不按 Agent 类型过滤：调用 `skill_manager.prompt_for(message, None)`，所有命中关键词的 Skill 都注入，总长度上限仍是 5000 字。沿用原项目"关键词命中即全文注入"的机制，不做 skill lookup 工具，也不做渐进式披露。
- 实现方式：在 `BaseAgent` 里加一个 `_skill_scope()` 方法，默认返回 `self.agent_type.value`，`SingleAgent` 覆盖成返回 `None`。
- 值得关注的差异：复合问题会同时命中技术和账单两份规则，单 Agent 的提示词会被塞满甚至截断；V3 每个垂类 Agent 只拿自己那份。评测时可以看出这对回答质量的影响。

### 5.5 记忆

和 V3 完全一样：接口层读取 Redis + ChromaDB 的记忆上下文，放进 `Request.context`，回答后写回。

### 5.6 实体

不调用意图识别。把 `IntentRecognizer._extract_entities` 里的正则抽取提成模块级函数 `extract_entities(message)`，V2 直接调用，抽取订单号、金额、日期、错误码。不调用模型。

### 5.7 转人工

由 Agent 根据 Skills 规则自己判断，需要时调用 `create_handoff_summary`。`escalated` 在两种情况下为真：调用了该工具，或回复命中转人工关键词。

### 5.8 失败处理

没有降级 Agent，失败时返回 `BaseAgent` 现有的致歉回复，`success = false`。V3 的"专属 Agent 失败降级到通用 Agent"属于路由能力，V2 不具备。

## 6. V3：包装现有编排器

`MultiAgentPipeline` 把现在写在 `/chat` 接口里的逻辑原样挪进 `run()`：

```text
意图识别（带最近对话）→ 构造 Request（实体、意图、紧急度）→ orchestrator.run → 转成 PipelineResult
```

行为不变。`extra` 里放 `intent`、`intent_group`、`intent_confidence`、`routing_reason`、`routing_confidence`、`primary_agent`、`supporting_agents`、`agent_types`。

## 7. 按请求统计模型用量（`core/llm_utils.py`）

- 新增 `UsageMeter`（调用次数、失败次数、输入 token、输出 token）和 `track_usage()` 上下文管理器，用 `ContextVar` 保存当前请求的计量器。
- 新增 `make_client(api_key, base_url)`：创建 `AsyncAnthropic`，并包装 `messages.create`，每次调用把 `usage` 累加到当前计量器。`asyncio.gather` 派生的子任务会继承同一个计量器，所以 V3 并行的多个 Agent 也会算进来。
- 把现有 5 处 `AsyncAnthropic(**kwargs)` 换成 `make_client`：`agents/agent_orchestrator.py`、`core/intent_recognizer.py`、`mcp/tool_manager.py`、`memory/conversation_memory.py`、`evaluation/evaluator.py`。
- 统计范围只包括生成回答这条链路。回答之后的记忆压缩和用户画像更新不计入，这几个版本在这部分完全相同。

## 8. 接口改动（`api/main.py`）

- `ChatRequest` 新增 `mode: Literal["v1", "v2", "v3"] = "v3"`。不传时行为和现在完全一致。
- `/chat` 分发：
  - **v1**：直接调用 V1，不读写记忆；没有 `conv_id` 时照常生成并返回。
  - **v2 / v3**：读取记忆 → 调用对应版本 → 写回两条消息 → 异步更新用户画像，与现在的流程一致。
- `ChatResponse` 新增 `mode`、`llm_calls`、`input_tokens`、`output_tokens`、`retrieved`。只有 V3 才有的字段（`intent`、路由相关）给默认值，V1、V2 留空；`agent_type` 在 V1 填 `rag_baseline`，在 V2 填 `single`。
- 启动时一并初始化三个版本。V1 从 `_tool_manager` 构造 RAG hook；V2 使用同一个 Skills 管理器和共享工具。
- V1、V2 的请求轨迹也写入现有的轨迹存储（在 `AgentOrchestrator` 上新增一个记录外部轨迹的公开方法），`/trace/tool/{request_id}` 三个版本都能查。

## 11. 测试（`tests/test_pipelines.py`，使用假模型客户端）

- **V1**：RAG hook 恰好调用一次且 `query` 为用户原话；生成调用不带 `tools`；system 里没有 Skills；不触碰记忆；检索失败或降级时提示词里是"（未检索到相关资料）"，仍能正常回答。
- **V2**：工具集等于 5.3 的列表；Skills 按 `prompt_for(message, None)` 合并注入；最多 5 轮工具调用；实体由正则抽取；调用转人工工具时 `escalated` 为真。
- **V3**：包装后的结果与直接调用 `AgentOrchestrator` 一致。
- **接口**：不传 `mode` 时走 V3；v1 不读写记忆。
- **用量统计**：`asyncio.gather` 并行的多个调用都被计入同一个请求。

## 13. 已知问题（本计划不处理，单独决定）

- **多路召回去重失效（已修复）**：`search_with_rewrite` 原来用整条结果的 md5 去重，但每条结果都带相似度分数，同一个片段被不同子查询召回时分数不同，去不了重，重排后的前 `top_k` 条里可能有重复片段。
  - 修复：`KnowledgeBase.search` 的返回结果加上 ChromaDB 的片段 `id`，`search_with_rewrite` 改为按 `id` 去重；没有 `id` 的结果（如知识库降级结果）沿用原来的方式。
  - 不按（标题，片段序号）去重的原因：片段 ID 是 `md5(标题_序号_内容前 50 字)`，标题和序号相同的片段可以同时存在多条，例如两篇同名文档，或同名文档改了内容后重新导入。
- **同名文档更新后旧片段残留（待修）**：修改内容后重新导入同一标题的文档，会生成新 ID 的片段，旧片段仍留在库里，检索可能命中过期内容。修复思路：写入前按标题删除旧片段。代码里已在 `KnowledgeBase.add_documents` 留了 TODO。
- **默认向量模型对中文效果一般**：知识库用的是 ChromaDB 默认的 all-MiniLM-L6-v2。
- **检索缓存影响延迟对比**：召回结果有 300 秒缓存，同一个问题第二次检索会变快。对比延迟时需要关闭或清空缓存。
- **Docker 访问本地模型的地址**：容器里的 `127.0.0.1` 指向容器自己。生成改用 DeepSeek 后不受影响；之后用本地模型打分时，容器内要用 `host.docker.internal:1234`。
