# 评测结果：原项目 V1/V2/V3 与 LangChain V3

> 日期：2026-10-04（Asia/Hong_Kong）
> 正式结果：`data/eval/runs/full-v3lc-prompt3-20261004/`（`report.md` 总报告、`answers.md` 逐题回答对照、`summary.json`）
> 脚本：`env -u ANTHROPIC_BASE_URL .venv/bin/python -m scripts.arch_eval --out data/eval/runs/<名称>`

## 1. 方法

- **评测集**：原项目 `data/eval/arch_cases.json`，共 30 题。7 个类别：知识库问答、用户数据类、知识库无答案、跨领域复合、升级/紧急、业务规则边界、多轮对话。多轮题按顺序发送，前几轮的回复由被测系统实时生成，只对最后一轮打分。
- **打分**：直接导入原项目 `evaluation/arch_eval.py` 的打分提示词、解析逻辑和汇总代码；本地裁判 `qwen3.8-27b`，温度 0。唯一的区别是客户端适配层：新环境的 anthropic SDK 1.x 需要通过 `extra_body` 传温度。
- **被测系统**：本项目 V3。每题都经过真实 `/chat`，即 Jev 路由、DeepSeek `deepseek-v4-flash`（关闭推理）、bge-m3 知识库（26 个片段）、会话存储（隔离的临时 SQLite）。检索缓存关闭，生成并发数为 3，与原评测一致。
- **原项目的三列**：V1/V2/V3 直接复用原项目 `full-20261004` 的生成结果和打分（2026-10-04 上午），没有重跑。生成模型、知识库和裁判与本次相同，但代码是当时的版本。

## 3. "改前"到"正式"之间改了什么

改前版本中，Agent 对"有依据文档"的题只有 29.6% 调用检索，其余直接凭常识作答。例如 A01 回答"微信/支付宝 1–3 天、银行卡 3–7 天"，与知识库不符（原项目 V2/V3 也有同样问题）。

**排查结论**：不是提示词没注入进去。截取到的请求里，检索要求和 `search_knowledge_base` 工具都在，是模型自己选择不用。原因有四点：
- 检索要求埋在 3,800 字系统提示词的开头；
- 开头一句是"先回应当前问题"；
- 账单 Skill 教的是"时效用'通常、预计'这类保守表述"；
- 角色契约要求输出里给出"时效边界"。

对照测试：只给一句简单的系统提示词时，同一模型不用强制也会自己检索。

**修改**（`app/runtime.py`）：
1. 共享的业务边界里去掉"先回应当前问题"；检索工作流只给 Agent，汇总节点不再收到。
2. Skills 区块标明"只规定处理流程和表达方式，不提供政策数字"。
3. 删除重复的路由区块，澄清标记并入角色输入包。
4. 系统提示词**末尾**加"[回答前必须执行]"清单：涉及规则、时效、费用、额度、适用条件、办理步骤或故障处理，先检索、按结果回答；检索不到如实说明，不用常识补数字；调用工具的那一轮不写给用户的话；最终回答完整独立。
5. P16 改为方案一，只返回最后一轮回答（与原项目一致）。否则检索增多后，模型在工具轮写的"I'll look up…"会被拼进回答。

改前到正式，通过的题从 18 道增加到 29 道，没有一道变差。新增通过的 11 题在正式版中都调用了检索（包括多轮追问 F03）。

## 4. 一次作废的结果（评测泄漏）

第一版清单里写了例子"退款多久到账、开票需要什么信息、积分怎么抵扣、能否货到付款、App 报错或闪退"，几乎是 A01、A04、F04、N01、A05 的原题。那次结果（93.3%）已作废，单独存放在 `data/eval/runs/leaked-examples-v3lc-prompt2-20261004/`。改为通用表述后重跑，得到正式结果 96.7%。两次结果只差 1 题，说明那些例子不是提升的主要来源，但正式数字只用没有泄漏的这一版。

## 5. 解读时的限制

1. **样本量小**：30 题中每 1 题约 3.3 个百分点；只跑了 1 次。泄漏版与正式版相差 1 题，可作为单次运行波动的参考。
2. **提升主要来自提示词，不是框架**：从"改前"到"正式"的提升来自检索约束提示词和 P16 处理。原项目 V3 如果用同样的提示词也可能提升，本次没有验证。和原项目 V3 的对比同时包含了框架迁移、Jev 路由、升级出口和提示词几方面的变化。
3. **路由门槛在这 30 题上校准过**：路由相关的指标（复合题、升级）偏乐观。
4. **原项目三列来自较早的代码**（当时 P16 使用拼接文字的临时修复），不是和本次同时重跑的。
5. **统计口径不同**：本项目的耗时包含会话写入；模型调用次数不含 Jev，原 V3 的调用次数包含意图识别那一次。耗时受 DeepSeek 当时负载影响，不同时段的结果不能精确比较。
6. **成本上升**：检索增多带来查询改写和重排调用，模型调用次数从 2.1 升到 3.3；输入 token 是原 V3 的约 4 倍，因为完整角色契约、Skills 和真实历史消息每次都会带上。
7. **裁判是本地 27B 模型**：原项目记录过它在需要结合上下文的条目上判断不稳定。建议抽查 `answers.md`。
